# 近期基线代码讲解稿

这份稿子可以按文件顺序直接讲，预计 15–18 分钟。核心主线是：先冻结数据和口径，再接入
近期方法，先做五篇诊断，只有质量和约束都通过才允许全量运行。

## 开场：这套代码解决什么问题

大家好，这部分代码用来回答一个很具体的问题：2025—2026 年的新长度控制方法，在相同
CAIL 文书、相同 450 字符预算下，能否公平地与 LegalFactAware 比较。

这里没有一开始就跑全部 942 篇，因为生成式模型的成本很高，而且中文法律任务可能与原论文
差异很大。整个流程分为四层：数据冻结、共同协议、方法适配、统一评测。任何方法先跑固定的
五篇，只检查能否运行、是否退化、是否守预算；通过后才考虑全量实验。

## 第一部分：预注册文件

首先看 `PREREGISTRATION.md`、`LCG_PREREGISTRATION.md` 和
`ZERO_SHOT_LC_PREREGISTRATION.md`。

这两个文件不是程序，但它们决定了程序能做什么。共同规则是：只使用 942 篇开发集，不读取
测试集；摘要预算统一为 450 个 Python 字符；模型超长时不能由评测器事后截断；输入最多保留
8192 字符，采用 head-tail 截取。

head-tail 的含义是同时保留文书开头和结尾。开头通常包含当事人和诉讼请求，结尾通常包含
法律依据和裁判结果。它是任务适配的一部分，所以结果不能冒充原论文原始结果。

LCG 的预注册还冻结了 Qwen2.5-7B、one-shot 示例、五轮 MH+IS、top-k 20、top-p 0.8、
temperature 0.7、repetition penalty 1.05 和 seed 0。先写这些再看输出，是为了防止根据五篇
结果反复挑参数。

## 第二部分：数据准备

第二个文件是 `prepare_cail_dev.py`。

它从已有验证包读取 942 条记录，拆成两个 JSONL。`cail_dev_942.jsonl` 保存 ID、原文、参考
摘要和目标预算；`legalfactaware_predictions.jsonl` 保存冻结的现有系统输出。

这里最重要的不是格式转换，而是三个检查：记录数必须是 942，ID 必须唯一，原文、参考摘要
和预测都不能为空。脚本还计算 SHA-256，防止服务器和本地使用不同版本。

LCG 另外需要 `prepare_lcg_demo.py`。它从 CAIL 训练集固定取一条 one-shot 示例，并检查该 ID
不在 942 篇评测集中。本轮固定的是 train row 0；一旦冻结，后续不能因为结果不好而换示例。

## 第三部分：共同协议

接下来看 `protocol.py`。它是所有方法共同依赖的基础层。

第一，字符预算使用 `len(text)`。第二，ROUGE 先去除空白，再计算字符级 ROUGE-1、2 和 L。
字符预算和 ROUGE 的字符序列不是同一个概念，讲解时要分清。第三，它抽取金额、日期、法律
条文和裁判结果四类 Expression。第四，它计算预测表达在原文中的支持率。

来源支持率只能说明某个金额、日期或法条字符串能在原文找到，不能说明整句话逻辑正确。因此
代码不会把它命名成“事实准确率”。

## 第四部分：DELTA 适配

`vendor/delta-diffusion/` 保存 DELTA 官方核心代码、README、许可证和源码清单。
`run_delta_cail.py` 位于 vendor 外部，不直接改作者实现。

这个入口负责读取 CAIL、构造中文提示、把 450 字符换算成扩散模型所需的长度空间，并逐篇
保存结果。它支持断点续跑，每篇完成后立即写入 JSONL。真正的扩散长度调整仍由官方
`generate_length_controlled` 完成。

五篇测试表明，DELTA 可以稳定生成 445–448 字符，工程链路是通的；但输出有重复、数字串、
英语占位词和事实错误，ROUGE-L 只有 15.70，而 LegalFactAware 是 45.27。随后没有直接把
这五篇当正式证据，而是先在 XSum 原任务上做 50 篇回归验证。长度 MAE 为 2.0，门槛通过后
才完成 942 篇 CAIL 适配。全量 DELTA 的 ROUGE-L 为 19.95，55/942 超过 450 字符。

## 第五部分：LCG 的长度与接受概率

LCG 先看 `lcg_protocol.py`。

它实现两种距离。`upper_budget_distance` 只惩罚超过 450 的部分，450 以内距离都是 0；
`exact_target_distance` 使用与 450 的绝对差。前者对应论文任务的硬上限适配，后者更接近
原论文“指定目标长度”的机制。

`acceptance_probability` 实现 MH+IS 的接受上界。直观地说，候选越接近长度目标、同模型
裁判给出的质量比越高，就越容易被接受。满足目标的候选直接接受。`extract_score_pair` 负责
从模型输出的 JSON 或文本中解析两个摘要的总分，解析失败时不会伪造分数。

## 第六部分：LCG 主流程

核心文件是 `run_lcg_blackbox.py`，按运行顺序分成五步。

第一步，加载 Qwen2.5-7B。GPU 运行使用 4bit NF4，只是部署适配，论文必须披露。

第二步，`initial_messages` 构造 one-shot 提示，先让模型直接生成摘要。初始输出单独保存，
这样可以把“直接提示”和“LCG 搜索后的结果”放在同一个评测器中比较。

第三步，如果当前输出还没有满足长度目标，`proposal_messages` 要求模型压缩或扩写。差距不超过
3 个字符时，会明确要求增加或删除对应字符；差距较大时则重新组织摘要。

第四步，`judge_messages` 让同一个模型从信息覆盖、流畅、简洁、连贯和忠实五方面比较新旧
摘要。随后代码根据长度比、质量比分别计算接受概率，并用固定 seed 的随机数决定是否接受。

第五步，每篇保存初始长度、最终长度、预算违规、每轮候选长度、裁判分数、接受概率、随机数、
是否接受和耗时。这个 trace 是复现和解释失败原因的关键，不能只保存最后一段文本。

## 第七部分：为什么有两种 LCG 结果

预注册主结果使用 `--length-objective upper_bound`，因为正式任务是“不超过 450 字符”。五篇
初始摘要只有 185–267 字符，全部已经合法，所以搜索轮数为 0。最终 LCG 与 Qwen 直接提示
完全相同，ROUGE-L 为 32.29，比现有系统低 12.98 点。

为了判断是否只是目标定义造成失活，又增加了 post-hoc 的 `exact` 探索。它允许把偏短摘要
扩到接近 450 字符。结果的 ROUGE-L 提高到 38.87，与现有系统差 6.40 点；但 2/5 超预算，
来源表达支持从 100% 降到 94.53%，并出现内容重复。

搜索轨迹还暴露了一个机制问题：同一个 Qwen 同时负责生成和裁判，几乎每轮都给 47–49 分，
质量比接近 1，裁判区分能力有限。所以不能因为精确长度版看起来更接近，就直接跑 942 篇。

## 第八部分：Zero-Shot LCS

第三个方法先看 `zero_shot_lc_protocol.py`。它对应 Findings of NAACL 2025 的
*Zero-Shot Strategies for Length-Controllable Summarization*。

`select_candidate` 实现 Sample Filtering。论文忠实的 exact 口径选择与 450 绝对差最小的
候选；任务适配的 upper 口径先排除超预算候选，再选择最接近 450 的合规候选。整个选择过程
只看长度，不读取参考摘要或 ROUGE，因此没有测试标签泄漏。

`is_compliant` 把两种停止条件分开：exact 使用论文的正负 10% 区间，upper 使用严格不超过
450。`revision_feedback` 把当前字符数和差值反馈给模型，最多修订 5 轮。

再看 `run_zero_shot_lc.py`。每篇先独立采样 3 个候选，保存全部文本和长度，再选出一个候选。
若不合规，就按照论文模板逐轮修订；每轮只使用上轮摘要，并保存新文本、长度和 seed。代码
使用未闭合的 Qwen assistant prefix 复现论文的 prompt prefilling，兼容服务器上的
Transformers 4.41。

5 篇 exact 诊断只有 2/5 进入正负 10% 区间；upper 版 5/5 不超预算，但平均只有 179.8
字符。工程门槛通过后，upper 版扩到冻结 100 篇。300 个初始候选中只有 1 个超过 450，
每篇都能直接选到合规候选，因此自动修订总次数为 0。最终平均 185.14 字符，ROUGE-L
28.99，Expression F1 25.53；LegalFactAware 分别为 53.38 和 47.30。

这组结果的重要解释不是“论文方法错误”，而是它的修订触发条件和我们的单侧预算任务不
匹配：只要摘要偏短，就已经合法，修订机制不会启动。

## 第九部分：统一评测

`evaluate_cail_baselines.py` 负责最后的统一比较。

正式模式会检查每种方法的 ID 集合是否与 942 篇完全一致。五篇诊断使用显式 `--limit 5`，
避免把缺少 937 篇误当成完整结果。

逐篇计算的内容包括：ROUGE-1、2、L，文档宏平均 Expression F1，四类分类型指标，来源表达
支持率，实际长度、与 450 的绝对误差和预算违反。多方法时，以第一种方法为锚点做逐文档
bootstrap。五篇样本只报告描述性数值，不解释置信区间和显著性。

## 第十部分：自动测试

`tests/test_protocol.py` 检查字符计数、完全匹配 ROUGE、空输出、head-tail 和四类 Expression。
`tests/test_frozen_dev.py` 用全部 942 篇固定平均长度 396.485 和 Expression F1 0.478526。
`tests/test_lcg_protocol.py` 检查上限距离、精确距离、接受概率和裁判分数解析。
`tests/test_zero_shot_lc_protocol.py` 检查三候选排序、正负 10% 区间、硬上限和修订反馈。

当前 25 项测试全部通过。它们保证的是程序口径和回归值，不保证生成模型的摘要事实正确。

## 结尾：最终判断

最后总结，这套代码已经完成三个近期方法的真实 GPU 适配，并且保留了模型身份、输入、输出、
逐轮轨迹和统一指标。结果不是“所有新方法都不如我们的系统”，而是更克制的三点：

第一，DELTA 在当前中文法律底座上发生明显生成退化。第二，LCG 的精确长度目标与我们的硬上限
任务存在结构性差异。第三，Zero-Shot LCS 在单侧上限下不触发修订并系统性偏短。第四，
LegalFactAware 在统一 100 篇上保持更高摘要指标和零预算违规。

因此，五篇结果只作为验收，不进入正式主表；冻结 100 篇可进入单独的资源受限比较表，
DELTA 942 篇可进入完整开发集的生成式对照表。所有方法都必须写明 CAIL adaptation，不能
把中文 4-bit 适配结果外推为原论文英文任务的总体优劣。
